# minilakehouse — agents: design, 2026-10-24

How an AI agent works for a person, with its work tied to that person and to a session, without
weakening what `PROVENANCE.md` guarantees and without asking the person for anything per piece of
work. Assumes `docs/PLAN-2026-10-24.md` items 1 to 5 are built. The Keycloak behaviour it depends
on was checked on Keycloak 26.6.1, the version the stack runs; the last section lists what was run.

## In brief

- An agent is a Keycloak client. It acts with the person's rights and holds none of its own.
- The person connects an agent once. The agent then has a login of its own, separate from the
  person's, that lasts until they disconnect it.
- That login has its own session pointer. The agent never moves it; the person can.
- By default all of an agent's work for a person lands in one session, named after the agent.
  That errs toward more candidate sources, never fewer.
- The person's attention goes where the design already puts it: at the exit, declaring what an
  output was made from, which the agent can draft. Whatever widens who may read something stays
  the person's act.
- The agent can query what its session holds: `governance.session_sources`.

## Why the agent needs its own login

Every read made through the platform before a write is a candidate source of that write, within
the write's session (`PROVENANCE.md` 4, 5.2). Governance learns a request's session from a
pointer it keeps per login, keyed by person and Keycloak `sid`.

Moving a pointer to another session is a claim: that whatever uses the login carries nothing from
before. Call that the environment: a notebook, a Trino client, an agent's context window, anything
that holds data between requests. The claim holds only if one environment uses the login and that
environment's owner makes it.

An agent the person authorizes in their browser gets the same `sid` as the person's own clients in
that browser (checked), so the two would share one pointer, and a switch by either would move the
other's session out from under it. And an agent cannot make the claim about itself: what it read
stays in its context, and what it reads can instruct it.

So the agent gets a login of its own, and only the person moves its pointer.

## Connecting an agent

Once per agent, like connecting any app to an account.

1. **The agent asks.** It sends Keycloak a CIBA request (Client-Initiated Backchannel
   Authentication, a supported Keycloak grant) naming the person, asking for `offline_access`.
2. **The person approves once.** Keycloak's CIBA authentication channel is pointed at governance,
   which shows the request in the person's inbox: which agent wants to work for them.
3. **The agent has its own login.** Its tokens carry a new `sid`, never the browser's, with an
   offline refresh token. The login survives the person signing out of their browser, and lasts
   until the person disconnects the agent or it goes unused for Keycloak's offline idle limit
   (30 days by default). Refreshed, or exchanged for another audience, its tokens keep its `sid`
   (all checked).
4. **Its work goes to the agent's session.** The first time governance sees the login, it points
   it at the person's session named after the agent, `assistant` for client `assistant`, starting
   it if need be. This replaces, for agent logins, the rule that a new login continues the
   person's most recently used session.

Disconnecting ends the login in Keycloak. The session and everything recorded in it stay.

## Sessions for agent work

- **The agent never moves its pointer.** A session insert, or `POST /sessions`, on an agent's
  login is refused. Concurrent conversations through one connection share its session, which pairs
  more reads with each write, never fewer.
- **The person moves it, when it's worth it.** `PATCH /me/agents/<client> {"session": name}`
  from the person's own login points the agent at a new or existing session, as switching their
  own does today. It is the same claim, made about the agent's environment, and it moves every
  conversation the agent has open on that connection: the time to make it is when the agent starts
  fresh work, a new chat say. Nothing requires it.
- **The person's own logins are untouched.** Their pointers move only by their own lever, as now,
  and nothing an agent does moves them.

## The exit

A coarse session costs nothing until an output goes to someone who may not read one of the
sources the session held. That is the moment `PROVENANCE.md` already asks for the person's
attention, as trusted research environments do at their airlock: declaring which candidates an
output used. Two things make it cheap:

- **The agent drafts the declaration.** It knows which tables its statements used for which
  output, so it files a draft as Trino's listener does (handoff 4). The person confirms with their
  own login, and the confirmation runs every check an insert would.
- **The agent can see it coming.** `governance.session_sources` tells it, before it writes,
  whether the intended readers can read the result, so it can say so instead of producing
  something they cannot open.

## Rules

- **Agents get tokens only by CIBA.** An agent client has the CIBA grant and token exchange, and no
  browser sign-in or password grant, so it never holds a token from the person's browser login.
  As a backstop, governance refuses an agent client's token on a login a person's own client used
  first.
- **The login decides, not the token.** Trino's Iceberg client refreshes a long query's token by
  exchanging it as the `trino` client (`WHITEPAPER.md` 6); the token that comes back is issued to
  `trino` but carries the agent login's `sid` (checked). Keycloak lets a client exchange only a
  token issued to it or naming it as an audience, so an agent asks for `trino` as an audience
  too; without it, a query outlasting the token fails at its next catalog call. Every rule here is
  keyed on the login.
- **Agents draft, people sign.** For a request on an agent's login, OPA refuses a declaration that
  marks a source unused, a grant change, publishing, a transfer, a release request or approval,
  and a group change. The agent drafts them; the person confirms. A person who wants an agent to
  sign for them runs it on their own login, and it is then their signature.
- **The record.** An agent's login keeps the client, who approved it and when. Access-log rows
  already carry the `sid`, so every row on an agent's login is that agent's, whichever client's
  token it arrived with. `GET /me` lists the person's connected agents and the session each is in.

### Why the guarantee still holds

A write's candidates are the reads of its session, and a request's session comes from its login.
An agent's login is used by that agent alone and moves only when the person moves it. A person's
login moves only when the person moves it, as today. So no environment's reads leave its session
except by a claim its owner made.

Two things stay as they are. A person's own clients still share one browser login, and a switch
in one moves the others; that is the person's claim about their own environments. And an agent
that keeps memory outside the platform carries it across sessions, as a person carries a download
(`PROVENANCE.md` 8).

## What a session holds

`governance.session_sources`, read-only, served like the other `governance` tables. One row per
source that anything a session writes now would carry: each dataset the session read, and each
source that arrived through those reads.

| column | meaning |
|---|---|
| `session` | the session's name |
| `source`, `source_type` | the source, as `governance.lineage` names it |
| `direct` | false for a source that arrived through a read |
| `read` | the groups that may read data carrying this source as it arrived: the source's effective `read`, plus groups released past it on every path it arrived by. Empty when the person may not describe the source |

Before writing a table meant for projw:

```sql
SELECT source FROM governance.session_sources
WHERE session = 'assistant' AND NOT contains(read, 'projw');
```

No rows: projw will be able to read it. Otherwise the rows are the sources in the way, and the
choices are the existing ones: declare a source unused if the output did not use it, ask its owners
for a release, or redo the work in a fresh session. The answer is for the group as a whole; a
member may still read through another group.

## Checks, `seed/check-agents.py`

1. alice connects `assistant`. Its Trino read of `t1` and its broker credential for
   `projx/public` are both stamped with session `assistant`, on the agent's login.
2. alice's own pointer has not moved; her next read is stamped with her own session.
3. A session insert from the agent's login is refused. alice's `PATCH /me/agents/assistant`
   moves it, and the agent's next read is stamped with the new session.
4. alice signs out of her browser; the agent keeps working on its login.
5. `assistant` cannot sign in through alice's browser. A test agent client with browser sign-in
   left on can; its tokens carry her web UI's `sid`, and governance, the gate and the broker
   refuse them.
6. A declaration from the agent's login marking `t1` unused is refused; the same rows confirmed by
   alice are accepted.
7. After the agent reads `t1`, `session_sources` for `assistant` shows `t1`, and `projw` is not
   in its `read`.

## Changes

- `keycloak/realm-lakehouse.json`: a confidential client per agent, with the CIBA grant and
  standard token exchange on, browser sign-in and the password grant off, the `principal_name`
  mapper and the audience scopes, including a new `aud-trino`; the `offline_access` role for
  people, whom the realm file gives no roles today; and Keycloak's CIBA authentication channel set
  to governance's route
  (`--spi-ciba-auth-channel-ciba-http-auth-channel-http-authentication-channel-uri`).
- `governance/app.py`:
  - The channel route: verifies Keycloak's signature on the request, puts it in the person's
    inbox, and calls Keycloak back with the decision.
  - `agent_logins (person, sid, client, approved_by, approved_at)`.
  - `_pointer`: an agent client's first request on a login points it at the person's session
    named after the client; refused if a person's client used the login first.
  - `_switch_session`: refused on an agent's login. `PATCH /me/agents/<client>` moves it, from the
    person's own login only.
  - The `azp` check accepts registered agent clients.
  - `governance.session_sources`.
- `gate/app.py`, `broker/app.py`: pass `azp` to the access log; accept registered agent clients.
- `opa`: the refusals under "Agents draft, people sign", keyed on whether the request's login is
  an agent's.
- The web UI: connected agents and their sessions on the person's page; connection requests and
  drafts in the inbox.

## Options

- **A session per conversation, without asking.** A harness the platform runs itself knows where
  each conversation begins, which an outside MCP client does not tell a server. Such a harness can
  be allowed to connect once per conversation, with governance approving each request
  automatically under the person's standing connection, and to name each login's session once, at
  its first request. That gives exact sessions with no friction, by trusting the harness, never
  the model, with the claim.

## Rejected

- **An approval for each piece of agent work.** Exact, but the person is asked constantly, and
  approvals asked for constantly stop being read.
- **A pointer per client on a shared login.** An environment that uses two clients is split in two,
  and its writes lose candidates.
- **A shared login whose pointer agents may move.** An agent's switch moves another environment's
  session.
- **A shared login whose pointer only the person moves.** The person's switch in their notebook
  moves a running agent.
- **The session as a claim in the token**, through Keycloak's parameterized scopes (preview in
  26.8). The agent would make the claim about itself.
- **RFC 8693 delegation**, a token with `act` naming the agent (preview in Keycloak 26.8). Its
  tokens carry no `sid`, and `azp` already names the agent.

## Checked on Keycloak 26.6.1

Run on 2026-10-23 against a local Keycloak 26.6.1 with `keycloak/realm-lakehouse.json` imported
and the audience scopes `keycloak/setup.py` creates.

| What | Result |
|---|---|
| `trino`, then a second client, signed in from one browser | same `sid`; `azp` differs |
| An offline token from the browser | the browser's `sid` |
| CIBA for alice while her browser login is live | a new `sid`, different on each request |
| CIBA with `offline_access` | an offline refresh token; refreshes keep the `sid`; still works after alice signs out of her browser |
| Refresh, and standard token exchange for another audience | keep the `sid`; an exchanged token's `azp` is the client that exchanged |
| `trino` exchanging a CIBA login's token, as Trino's Iceberg client does to refresh | refused ("Client is not within the token audience") unless the token names `trino` as an audience; then issued to `trino`, same `sid` |
| An agent client with browser sign-in and the password grant off | both refused (`unauthorized_client`); CIBA and exchange of its own tokens still work |
| What the channel receives | `login_hint`, scope, binding message, and a bearer token signed RS256 with the realm key, naming the agent as `azp` |
| The person declines | the agent's next poll gets `access_denied` |
| `offline_access` for a user from the realm file | refused ("Offline tokens not allowed") until the user has the `offline_access` role |

Not checked: offline logins across a Keycloak restart and at the 30-day idle limit; the channel
behind governance's internal TLS listener.
