# minilakehouse — implementation handoff, 2026-10-20

Current state of the running prototype, for whoever picks it up next. The other docs serve
different purposes: `WHITEPAPER.md` is the target design, `DESIGN.md` describes the code and
rationale, and the root `HANDOFF.md` is the BERDL/Gravitino review that set this round of
work in motion. This file records what is actually built and running as of this date, what
has been checked, and what is open.

Work lives on branch `identity-passthrough-grants-out-of-opa` (head `e105c72` when this was
written). Nothing is merged to `main`.

## Shape of the system

One policy engine (OPA) decides; every other service either asks it or obeys a credential it
gated. OPA is on the decision path, never the byte path.

| Component | Role now |
|---|---|
| Keycloak | The only token issuer. Holds users (`alice`/`bob`/`carol`) and the `trino` client. Proves identity; holds no group membership. |
| governance | PAP + dataset and table registries (Postgres). Holds group membership and the only copy of every grant. Serves them to OPA (`/internal/*`), serves discovery, keeps the registry fresh against storage, accepts governed ingest (`POST /datasets`) and table registration (`POST /tables`), records the table lifecycle the gate reports, and creates each person's Polaris principal on first use (`POST /principals/me`). Holds only a least-privilege RGW reader. |
| OPA | The PDP, reachable only by its callers. Rules only: `policy.rego` (Polaris's checks), `tables.rego` (who may view/create a table or namespace — shared by Polaris's checks and the gate), `blob.rego` (files), `governance.rego` (the one fetch that gets a person's groups and the grants each rule needs). |
| gate | The only way to Polaris. Verifies the caller's token; trims listings to what they may view, with its own paging; maps a refusal for a name they may not view to not-found; retries a credential-refused table load without the credential so a see-only person can DESCRIBE; decides table and namespace creation (Polaris authorizes those against the parent only); reports creates and drops to governance; has governance create a person's Polaris principal before their first request; refuses register/rename and paths Polaris would rewrite. |
| Polaris | Iceberg REST catalog. Validates Keycloak tokens (audience `polaris`), delegates every operation to OPA, vends per-table STS. Reachable only through the gate. |
| broker | Blob vending (Flow C): verifies the client's own token, asks OPA about the named dataset, assumes a role scoped to the folder in OPA's decision. |
| login-proxy | In front of Trino so a client session outlives the 5-minute token. Speaks Trino's external-authentication protocol, holds the person's refresh token, forwards a fresh token on every request as the bearer and the `token` extra credential. |
| Trino | Query engine. JWT auth over HTTPS; forwards the person's token to Polaris (through the gate) as the `token` extra credential; reads files with the credential Polaris vends. |
| Ceph RGW | S3 + STS + bucket notifications. Enforces every vended credential. Storage is ephemeral (no volume). |
| Postgres | Polaris metastore and the durable `governance` database (named volume). |

Three Docker networks: `default`; `policy` (internal — OPA and its callers only); `catalog`
(internal — Polaris, its backends, the gate, and Polaris's setup jobs). OPA and Polaris
publish no host port; Polaris is reachable only through the gate.

## Grant model as implemented

- **Files/blobs.** A dataset entry carries a prefix and two group sets: `visibility` (see)
  and `access` (read). `register_grants` maps a group to the prefix roots it may register
  under; the `stewards` group is the capability to register at all.
- **Tables.** A `table_entries` row carries the id (`<catalog>.<namespace...>.<table>`) and
  four group sets — `see`, `read`, `write`, `delete` — plus status and location. `write`
  implies `read`; `delete` is required to drop and is implied by nothing. `namespace_owners`
  maps a group to a namespace it owns (and everything under it).
- **Groups.** `group_members` maps a group to a person. Membership is read at decision time,
  so a change applies at the person's next request. Tokens carry no groups.

Seed data for all of the above is `governance/registry.json`, loaded once into Postgres on
first boot.

## Identity path

The person authenticates to Trino with their own Keycloak token (audience `polaris`) and
attaches the same token as the `token` extra credential. Trino's Iceberg client sends it to
Polaris (through the gate) as the bearer, unexchanged. Polaris names the principal from the
token's `principal_name`; OPA fetches that principal's groups from governance. The broker and
governance verify the person's own token directly. A client that logs in through the
login-proxy holds an opaque session id instead, and the proxy swaps in a fresh token per
request.

## Checked on the running stack

Run during the work that produced this handoff, not a standing test suite:

- alice reads `db.t1`; bob, with no grant, gets "schema does not exist" (the same answer as a
  name that does not exist); naming another user is refused as impersonation.
- A see-only person can DESCRIBE a table through the gate; their SELECT fails at storage and
  their INSERT fails with Trino's vended-credential error (not a clean access-denied — see
  open items).
- File discovery and broker vending resolve groups from governance; a governed registration
  is allowed for a steward whose group owns the prefix and refused otherwise.
- Gate: listings are trimmed and paged; an unviewable name reads as not-found; creating a
  table requires it to be registered (pending) with the caller in its `write`; dropping needs
  `delete` and purges the files; register/rename and path-rewrite tricks are refused.
- Polaris logs no user tokens; a seeded-but-unknown user (carol) is created on first use; the
  `provisioner` principal may only create principals.
- login-proxy: log in once, reuse the session across queries, bob denied, impersonation
  refused; token refresh exercised by forcing it on every request.

## Open

1. **Polaris external-principal mode.** Released Polaris refuses a token whose name has no
   stored principal, so governance creates one per person on first use. When a Polaris release
   includes PR #5119 (`external` credential mode, merged on main 2026-09-24, not in 1.8.0),
   set `polaris.authentication.credential-mode=external`, pin that release, and remove the
   provisioner, the `POST /principals/me` endpoint, and the gate's call to it.
2. **No API to change membership or grants.** Both change only by editing governance's
   database; there is no endpoint or authorization model for the change itself.
3. **See-only INSERT message.** A see-only INSERT fails with Trino's "Failed to initialize the
   vended credentials" rather than access-denied. The only clean fix found was Trino's
   access-control plugin, which adds a second place that decides access; left unbuilt by
   decision.
4. **Login-proxy real-world checks.** An actual CLI `--external-authentication` browser run
   and a refresh after a true 5-minute token expiry were not run (each needs a browser or a
   timed wait); the protocol and refresh were exercised by a scripted login and a forced
   refresh instead.
5. **Login-proxy production hardening, parked.** Sessions are in memory (a restart logs
   everyone out); no browser confirmation page naming the client; flood controls beyond the
   per-source challenge rate limit depend on deployment topology (a trusted proxy and
   validated `X-Forwarded-For`, IPv6 /64 bucketing, distributed rate limiting). A single
   in-memory instance has an irreducible cap-vs-eviction tradeoff under a distributed flood.
6. **Larger whitepaper pieces, not started.** `share` grants, `write` for file datasets,
   derived datasets with inherited grants and widenings, a per-service token audience.
7. **Production hardening, not started.** Polaris still holds the RGW admin key; the storage
   events endpoint is unauthenticated; notifications are not persistent; everything but
   Trino's and the proxy's token ports is plaintext; dev credentials live in `.env`.

## Running it

```bash
docker compose up -d --build --wait      # bring the whole stack up
q alice -f /seed/seed-table.sql           # seed the demo table (q is defined in README.md)
```

Gotchas, learned the hard way:

- When recreating a single service, use `docker compose up -d --no-deps <svc>`. A plain `up`
  can re-run the `polaris-setup` one-shot, which **drops and recreates the catalog** — the
  namespace and tables vanish from Polaris (the RGW files and the governance registry remain).
  After that, or after the `ceph` container is recreated (its storage is ephemeral), re-run
  `ceph-setup`, `rgw-setup`, `polaris-setup` as needed and reseed the table. If governance
  still lists the table as `live` while Polaris has lost it, set that `table_entries` row back
  to `status='pending'` before reseeding, or the gate refuses the create.
- `README.md` defines the `q` helper (one fresh token per command) and `seed/proxy_login.py`
  (log in once through the proxy and reuse the session).
- A spare container on the host may already hold OPA's old host port; this stack's OPA
  publishes no host port, so that does not conflict.
